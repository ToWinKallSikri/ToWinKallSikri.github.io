FAT16 File System Reconstruction

A Python tool for recovering files from a FAT16 disk image after a quick format removed the root directory entries.

Overview

The assignment involved examining a FAT16 image whose root directory had been wiped by a quick format. With the directory entries gone, recovery depended on reading the filesystem structures and following the cluster chains directly.

I wrote a tool to map clusters and reconstruct file contents from the image, while checking the filesystem's two FAT copies and preserving the image as evidence.

My contribution

  • Parsed the FAT16 structures needed to locate and follow file cluster chains.
  • Handled 2,048-byte clusters and reconstructed file data from raw image content.
  • Compared FAT1 with FAT2 when tracing allocation information.
  • Verified the image's MD5 hash to check that the source evidence had not changed.

How it works

The tool reads the volume structures, maps data clusters using the 2,048-byte cluster size, and consults the FAT entries to follow file chains.

The two FAT copies are checked against one another. Reconstructed content is then written out for examination, with the original image hash retained as an integrity check.

Key decisions

Work from the image, not the live filesystem

Choice: Treat the disk image as the source of truth and verify its MD5 before analysis.

Why: Forensic work needs a reproducible input and a check that the evidence has not been altered during handling.

Trade-off: A matching hash establishes that the image stayed consistent; it does not prove that the image itself was collected correctly.

Follow cluster chains directly

Choice: Use FAT allocation entries to reconstruct file content instead of relying on the erased root directory.

Why: The directory records were missing, while allocation information remained available for tracing data clusters.

Trade-off: Recovery quality depends on the state of the allocation tables and how much the quick format had overwritten.

Results

The reconstruction recovered 57 files, 8 directories and 16 sub-directories.

Two notable recovered files were INVOICE.PDF and TRANSA-1.TXT. Their contents provided matching wallet information for the case exercise.

Limits and next steps

A quick format can leave useful allocation information behind, but recovery is not guaranteed if metadata or cluster contents have been overwritten.

Next, I would add a clearer recovery log that records each chain decision and flag inconsistent FAT entries for manual review.
