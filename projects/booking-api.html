Overview

This project is a .NET 8 API for managing bookings and availability. It uses Entity Framework Core with SQL Server and exposes paginated availability results, with Swagger for exploring the API.

The project is also a useful example of why authentication features need to be reviewed as carefully as the rest of an application.

My contribution

  • Built the API around EF Core and SQL Server.
  • Added FluentValidation rules for booking inputs, including overlap checks.
  • Implemented paginated availability and Swagger documentation.
  • Added JWT authentication with HMAC-SHA256 signing and a 30-minute expiry.

How it works

The API validates incoming booking data, checks for overlapping bookings and uses EF Core to persist records in SQL Server.

Availability queries are paginated. JWTs are signed with HMAC-SHA256 and expire after 30 minutes; Swagger provides an interface for exploring the documented endpoints.

Key decisions

Validate booking rules before persistence

Choice: Use FluentValidation to check booking inputs and overlapping time periods.

Why: Keeping validation explicit makes the booking constraints easier to understand and test.

Trade-off: The database and application validation need to remain consistent when concurrent requests arrive.

Limit token lifetime

Choice: Issue JWTs with a 30-minute expiry.

Why: A finite lifetime reduces how long a leaked token remains valid.

Trade-off: Expiry alone does not address insecure password handling, token storage or revocation.

Results

The project brings booking validation, persistence, authentication and API documentation together in one .NET 8 service.

The repository provides the implementation for further review and testing.

Limits and next steps

Passwords are currently compared in plain text. This is not safe for a real service and must be replaced with a well-reviewed password-hashing approach before deployment. JWT signing does not correct this weakness.

Next, I would implement salted password hashing with a suitable library, add tests for authentication and concurrent booking conflicts, and review authorisation and token handling before considering deployment.
