Overview

I built a learning-focused network intrusion detection system to inspect traffic and raise alerts when observed activity crossed configured thresholds. The project also explored how a monitoring tool can protect the integrity of its own logs.

It demonstrates a pipeline and several security mechanisms, but it is not a replacement for a maintained production IDS.

My contribution

  • Built a Scapy-based packet sniffer and traffic tracker.
  • Added threshold-based detection with a cooldown to reduce repeated alerts.
  • Implemented the project's mutual CHAP exchange and AES-256, HMAC, CRC and timestamp checks.
  • Added HMAC-protected log records and a separate `check_logs.py` verification utility.

How it works

Scapy captures packets, and the tracker maintains traffic measurements used by the threshold rules. A cooldown limits repeated notifications for the same condition.

The project also demonstrates a mutual CHAP exchange and uses AES-256, HMAC, CRC and timestamps in its communication and logging design. The verification utility checks whether protected log data has been modified.

Key decisions

Track activity before alerting

Choice: Separate packet capture and traffic tracking from the threshold decision.

Why: Keeping the stages distinct makes the detection logic easier to test and change.

Trade-off: The thresholds are static, so they do not adapt to normal changes in network behaviour.

Make log tampering detectable

Choice: Authenticate log records with an HMAC and provide a verification script.

Why: An alert is less useful if the records used to review it can be changed without detection.

Trade-off: The prototype uses a hardcoded key, which is not suitable for deployment.

Results

The project produced a working prototype that joins packet observation, threshold rules and integrity-checked audit records.

The class and sequence diagrams document how the main components and their interactions were intended to work.

Limits and next steps

Static thresholds can miss behaviour outside the rules and can create false positives. A hardcoded key is a significant deployment limitation.

Next, I would move key material into managed configuration, add tests around malformed and replayed records, and evaluate detection quality on representative traffic before making any operational claims.
