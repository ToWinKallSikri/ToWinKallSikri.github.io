API di prenotazione in C#

Un’API di prenotazione con EF Core, SQL Server e regole di validazione per controllare la disponibilità e impedire sovrapposizioni.

Panoramica

Il progetto consiste in un’API .NET 8 per gestire prenotazioni e disponibilità. Usa Entity Framework Core con SQL Server e offre risultati di disponibilità paginati; Swagger permette di esplorare gli endpoint.

Il progetto mostra anche perché le funzionalità di autenticazione vadano sottoposte a verifiche rigorose quanto il resto dell’applicazione.

Il mio contributo

  • Ho realizzato l’API usando EF Core e SQL Server.
  • Ho aggiunto regole FluentValidation per i dati delle prenotazioni, inclusi i controlli sulle sovrapposizioni.
  • Ho implementato la disponibilità paginata e la documentazione Swagger.
  • Ho aggiunto l’autenticazione JWT con firma HMAC-SHA256 e scadenza dopo 30 minuti.

Come funziona

L’API valida i dati in ingresso, controlla che gli intervalli non si sovrappongano e usa EF Core per salvare le prenotazioni in SQL Server.

Le interrogazioni sulla disponibilità sono paginabili. I JWT sono firmati con HMAC-SHA256 e scadono dopo 30 minuti; Swagger offre un’interfaccia per esplorare gli endpoint documentati.

Decisioni chiave

Validare le regole di prenotazione prima del salvataggio

Scelta: Usare FluentValidation per controllare i dati delle prenotazioni e individuare intervalli temporali sovrapposti.

Motivazione: Rendere esplicita la validazione facilita la comprensione e il test dei vincoli sulle prenotazioni.

Compromesso: In presenza di richieste concorrenti, la validazione applicativa e quella del database devono restare coerenti.

Limitare la durata dei token

Scelta: Emettere JWT con una scadenza di 30 minuti.

Motivazione: Una durata limitata riduce il periodo in cui un token eventualmente sottratto rimane valido.

Compromesso: La scadenza, da sola, non risolve i problemi di gestione delle password, conservazione dei token o revoca.

Risultati

Il progetto riunisce validazione delle prenotazioni, persistenza, autenticazione e documentazione API in un unico servizio .NET 8.

Il repository contiene l’implementazione per ulteriori verifiche e test.

Limiti e sviluppi futuri

Al momento le password vengono confrontate in chiaro. Questa modalità non è sicura per un servizio reale e deve essere sostituita con un sistema di hashing delle password affidabile prima della pubblicazione. La firma JWT non corregge questa vulnerabilità.

Come passo successivo, implementerei l’hashing con salt tramite una libreria adeguata, aggiungerei test per l’autenticazione e le prenotazioni concorrenti e rivedrei autorizzazioni e gestione dei token prima di valutare una distribuzione.
